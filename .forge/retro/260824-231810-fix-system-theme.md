# 2026-08-24 — 시스템 테마가 적용되지 않는 버그 수정

## 계획 vs 실제
- 계획대로 된 것: 슬라이스 3개 전부 착지. `applyNativeTheme(choice)` 분리 · `applyTheme` 순서 교정 · 하네스 회귀 가드. DoD 전방 검사 3개와 회귀 가드 3개 모두 통과, 사용자 확인으로 보고된 증상 해소.
- 차이: 어긋난 것은 *무엇을 만들지*가 아니라 **어떻게 검증할지**였다. 계획은 `data-theme` 갱신 시점을 `MutationObserver`로 잡아 네이티브 호출과 순서를 비교하기로 했는데, 구현 중에 **그 방법이 잘못된 순서의 코드도 통과시킨다**는 것을 발견해 "호출 시점 상태 스냅샷"으로 교체했다.
- 계획에 없던 단계: **변이 시험**. 두 방향(항상 구체값 강제 / CSS 먼저)으로 코드를 깨뜨려 각각 2건 실패를 확인한 뒤 원복했다.

## 학습
- 다음엔 다르게:
  - **실행 순서를 `MutationObserver`로 판정하지 마라.** 콜백이 마이크로태스크라서 동기 기록(예: `invoke` 인터셉트)보다 **늦게** 들어온다. CSS를 먼저 적용한 잘못된 코드에서도 "네이티브가 먼저"로 읽힌다. 대신 **관측 지점에서 상대 상태를 함께 기록**한다 — 네이티브 호출 시점의 `data-theme`이 아직 이전 값이면 네이티브가 먼저였다는 뜻이고, 완전히 동기적이며 경합이 없다.
  - **통과하는 검사는 변이 시험으로 유효성을 증명한다.** 이 세션에서 하네스를 4개 만들었지만 "깨진 코드에서 실패하는지"를 확인한 것은 이번이 처음이다. `format`·`toolbar`·`popover` 검사에는 아직 그 증명이 없다 — 후속 후보.
  - **하네스는 시작 시 앱 상태를 기준값으로 되돌린다.** `popover` 하네스가 남긴 `markview.theme=dark` 때문에 `theme` 하네스 결과가 흔들렸다. 회고 `260823-002733a`는 "검증 후 원복"을 말했지만, 하네스가 늘어나면 원복을 한 곳에서 잊는 것만으로 나머지 전부가 오염된다.
  - **버그의 원인을 추측으로 두지 말고 의존성 소스를 읽는다.** `setTheme`이 창이 아니라 `NSApplication` 전체 appearance를 고정한다는 사실은 `tao-0.35.3`의 `set_ns_theme`을 직접 읽어 확인했다. 이 프로젝트는 Rust 크레이트가 `~/.cargo/registry/src`에 그대로 있으므로 그런 확인이 항상 가능하다 — 메커니즘 주장에 `[높음]`을 붙일 근거가 된다.
  - **덜 날카로운 설계 기록이 버그를 낳는다.** 의제에 "단일 `applyTheme(실효테마)`로 진입해 Tauri 창 테마를 갱신"이라고만 적혀 있었고, 구현이 그것을 "항상 구체값으로 강제"로 해석했다. 시스템 모드가 강제를 **풀어야** 한다는 것이 어디에도 없었다.
- 확인된 것:
  - DoD에 하네스 자동 검증을 명시적으로 넣은 덕에 사람 확인을 기다리는 항목이 3개(수동)로 줄었고, 그 3개도 OS 설정을 바꾸지 않고 볼 수 있는 형태(다크 → 시스템)로 좁혀졌다.

## 미해결
- **"새로 실행해도 틀리다"는 사용자 보고가 증거와 충돌한 채 남았다.** window-state 플러그인(`THEME` 플래그 없음) · Info.plist(외관 강제 키 없음) · `tauri.conf.json`(창 `theme` 없음) 어디에도 테마를 강제·복원하는 것이 없으므로 새 실행은 정상이어야 한다. UAT에서 사용자가 확인한 것은 세션 중 전환(다크 → 시스템)이었다. 새 실행이 여전히 틀리면 원인이 하나 더 있다는 뜻이다.
